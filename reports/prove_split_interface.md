## The stage ladder

| stage | credited when |
|---|---|
| `generated` | the submission contains at least one non-empty test file |
| `compiles` | the toolchain build succeeded; a compile or dependency failure stops the run at this stage and never counts as a failed proof |
| `executes` | forge (or hardhat) ran at least one test from the submission |
| `impact_reproduced` | on the vulnerable revision the expected test failed with the expected assertion signature, not an unrelated error |
| `patch_verified` | the same test file, unmodified, passed on the second revision |
| `behaviour_preserved` | the fixed revision still does what the feature did: the project's own test suite ran on the fixed revision, its result is compared against a vulnerable-revision baseline so pre-existing failures are not attributed to the fix, no new failure appeared, the targeted positive-path assertions passed, and the affected function is still present. A patch that deletes or disables the feature does not earn this stage. Without recorded regression evidence the task stops at `patch_verified` and is reported as not fully verified |

The grader reads the assertion, not the exit code: `grader_reads_the_assertion_not_the_exit_code` = True.

## Isolation

- the model sees: `['task_id', 'finding_id', 'repository', 'vulnerable_commit', 'prompt', 'submission_contract']`
- the model must not see: `['fixed_commit', 'expected_assertion', 'harness sources', 'per-test verdicts', 'any answer key or hidden test']`

## Leakage audit

- no fixed revision appears in any model-facing file
- no harness source or expected assertion appears in a public file
- tasks sharing one repository are reported as a single group so a split cannot be called project-held-out
- this split is leakage-audited under the criteria above; it is not and must not be described as contamination-proof
