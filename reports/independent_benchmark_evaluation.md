# Independent benchmark validity evaluation

Audit of VLUN benchmark families A–V for leakage, shortcut baselines, and
task validity. Written from the measurement outputs in
`reports/independent/audit.json` and
`benchmark/independent/secondary_holdout_manifest.json`, both regenerated by
the commands in [Reproduce](#reproduce).

This is an evaluation of the benchmark, not of the repository. The
repository's own gates pass; that fact is not evidence of anything here, and
is not used as evidence anywhere in this report.

**Headline: of 19 scorable families, 1 survives as clean evidence.** The
published micro-accuracy of 0.8725 for a majority-class baseline is not a
floor to beat — it is mostly the arithmetic of saturated families.

---

## 1. Method and independence

`scripts/independent_benchmark_audit.py` re-implements every check from the
benchmark files directly. It does not import `scripts/score_benchmark.py`'s
answers, its heuristics, or any repository gate output. The only thing
reused is the **scoring rule**, deliberately, so the two evaluations are
comparable: exact match on the lowercased projected scalar, labeled rows
only. Where this report says a number differs from a published one, the
difference is always because this audit fits baselines on train only and
scores the held-out rows, which the published baselines do not.

Two properties are enforced by test rather than by assertion:

- `TestAdditiveAndReproducible` hashes every file under `benchmark/` and
  `Vbeta/benchmark_vbeta/` before and after the audit and the holdout build,
  and fails if a byte changed. The layer is additive.
- `TestAuditInvariants.test_answer_leak_detector_fires_on_a_planted_leak`
  plants a known leak and requires it to be caught, so a detector that
  silently stopped matching cannot report the benchmark clean.

The holdout was built from the committed benchmark files and did not exist
while any published score was produced. No model, prompt or threshold was
tuned against it.

## 2. Leakage audit

### 2.1 Confirmed leakage

**K — the group key is the answer. `source_only_lookup` = 1.0000, coverage 1.0.**

Family K groups by the language prefix of the record id, and the record id
prefix *is* the gold label:

| group | gold labels |
|---|---|
| `cairo` | cairo ×8 |
| `move` | move ×15 |
| `rust` | rust ×18 |
| `solidity` | solidity ×45 |
| `vyper` | vyper ×51 |

A two-line lookup table scores **1.0000 with 100% coverage** on the official
test split. The repository documents this vector itself in
`benchmark/manifest.json`: *"task ids and `source` blocks carry the record id
for traceability and a record id carries its language prefix, which is family
K's answer."* The disclosure is accurate; the consequence is that K measures
lookup, not routing.

The same structure makes **O** (`record_class`) score 1.0000 from the group
key and **P** (`highest_authority_tier`) 0.9032.

**K and L leak the answer into the evidence itself.** Measured on the
model-facing payload with the prompt and label vocabulary removed — a prompt
that ends *"Answer vulnerable or no_confirmed_vulnerability"* is
self-description, not leakage, and counting it would make every family look
compromised:

- K: the gold language appears in the task's own evidence in **78/137 rows
  (0.569)** — `affected_components` carries file paths like
  `ownable.cairo` (58 rows), plus `prose` (14) and `sources` (4).
- L: the gold severity appears in `published_severities` (68) and `prose` (26).

For K this is defensible — the extension *is* the evidence a router would
use — but it means K cannot distinguish recognition from string search. For
L it is more serious: copying a published severity is the whole task, and the
repo's own `first_published` baseline already does it perfectly on the 71
rows where a severity field is present.

### 2.2 Legitimate overlap, distinguished from leakage

Not everything shared is a leak. These are clean and are reported as clean:

- **Record-id overlap across train/test is zero in every audited family.**
- **No byte-identical code block and no shared code file path** appears
  between train and test for A or C (the two code-bearing families).
- **A/C repository overlap is zero** — the Code4rena split holds out whole
  contests on both sides.
- **Near-duplicate title overlap is zero** for every family except T.
- **5-gram Jaccard to the nearest train task** peaks at 0.455 (A) and 0.455
  (C); no held-out row in any family except T reaches the 0.9 threshold.

The one exception is **T**, whose two test rows are near-duplicates
(Jaccard 1.0) of train rows carrying the same label. With a test split of
2 rows this is not a scoring problem so much as a statement that T has no
test set.

### 2.3 Answer-distribution shortcuts

This is the most consequential finding, and it is a property of the splits,
not of any row.

| family | train majority | test rows | that majority on test | label-mix L1 |
|---|---|---|---|---|
| R `v3_R_source_tier_routing` | tier `1` | 107 | **0.0000** | 1.756 |
| C `C_attacker_reasoning` | unprivileged | 39 | 0.3333 | 1.030 |
| E `E_exploit_verification` | passes | 1 | 1.0000 | 0.667 |
| N `N_attacker_identity_extraction` | true | 3 | 1.0000 | 0.600 |
| K / L / O / P | — | 29–31 | — | 0.486–0.534 |
| A `A_vulnerability_detection` | no_confirmed | 147 | 0.5512 | 0.340 |

**R is the clearest case.** R's train split spans all three tiers
(0: 878, 1: 3517, 2: 611) while its validation *and* test splits are
**100% tier 2**, drawn from a single contest prefix
(`c4-reserve-findings`) that appears nowhere in train. The train-majority
predictor scores **exactly 0.0000**. Meanwhile TF-IDF retrieval over inputs
scores **1.0000** on the same rows. Both numbers are real; together they say
the R test split measures which contest a finding came from.

**A is subtler and worth stating precisely.** A's class prior moves sharply
across splits — vulnerable is 0.279 in train, 0.140 in validation, **0.449**
in test. A majority classifier therefore scores 0.721 / 0.860 / 0.551 on
train / validation / test *from the same constant prediction*. The repo's
README already calls this "a split-blind floor is a validity hazard"; this
audit quantifies it.

### 3.1 A coverage artifact in a published baseline

`reports/baselines/baseline_first_published.json` reports
`micro.accuracy = 1.0000`. It predicts on **71 of 22,149** scorable rows
(0.32%). The field is computed over predicted rows only, so it is not
arithmetically wrong — but quoted as a headline it says a copy-the-publisher
rule solves the benchmark. The repository's own `accuracy_scorable` in the
same file is **0.0032**, and the README does quote 0.0032. The defect is
that a field named `accuracy` exists without a coverage guard, and a machine
reader will take it at face value.

| baseline | micro accuracy | accuracy_scorable | coverage |
|---|---|---|---|
| first_published | 1.0000 | 0.0032 | 0.32% |
| majority_published | 1.0000 | 0.0032 | 0.32% |
| majority | 0.8725 | 0.8725 | 100% |
| retrieval | 0.8949 | 0.8883 | 99.93% |
| frequency (seed 7) | 0.8135 | 0.8135 | 100% |
| random (seed 7) | 0.3608 | 0.3608 | 100% |

### 3.2 Why micro-accuracy over 22,149 rows is not a headline

The 0.8725 micro figure is dominated by families where one class is ≥95% of
the rows. S (1056/1072), T (588/589), U (6063/6219), V (6900/6935) contribute
14,815 of the 22,149 scorable rows, each ≥98.5% solved by a constant
prediction; with the single-label families B, F, G, I, J, nine families at
≥95% majority span 15,075. Macro-F1 exposes what
accuracy hides: on V, majority-class
accuracy is 0.9998 but macro-F1 is **0.5000**, and on U it is 0.983 against
**0.1983**. Those are the numbers a reader should have been shown.

## 4. Secondary holdout and whether shortcuts survive

`scripts/build_secondary_holdout.py` builds two additive holdouts.

**Group-disjoint**: whole groups partitioned with a seeded shuffle,
stratified by majority label. Built for 7 families (L, N, O, P, S, T, U).
For 9 families the committed splits are *already* record-disjoint — every
group is a single row — so rebuilding cannot make them stricter
(`skipped_already_group_disjoint`). For **K, R and V it is refused with
evidence** (`skipped_group_determines_label`): every multi-row group carries
exactly one label, so the group key *determines* the answer and holding out a
group would hand the model the label for every row removed. Shipping such a
split would look rigorous and measure nothing.

**Class-disjoint**: all rows of the two rarest labels held out, then every
group touching a held-out row removed from the retained side. Built for 4
families; skipped for 15, with the reason recorded.

### The decisive result

Every shortcut that scores 0.84–1.00 on the official splits scores
**exactly 0.0000** on a class-disjoint holdout:

| family | held-out labels | rows held / kept | majority | random | input retrieval | *oracle peek* |
|---|---|---|---|---|---|---|
| K | cairo, move | 23 / 114 | 0.000 | 0.000 | 0.000 | 0.652 |
| P | 1, 3 | 58 / 69 | 0.000 | 0.000 | 0.000 | 0.828 |
| R | 0, 2 | 1950 / 3517 | 0.000 | 0.000 | 0.000 | 0.550 |
| U | cairo, move | 39 / 505 | 0.000 | 0.000 | 0.000 | 0.513 |

Input retrieval goes from **0.839 → 0.000** (K), **1.000 → 0.000** (R),
**0.871 → 0.000** (P), **0.900 → 0.000** (U). Group lookup goes from
**1.000 → 0.000**. This is the answer to the question the benchmark was
supposed to answer: the apparent performance came from the label and group
composition, not from the task.

The `oracle peek` column is the accuracy a constant predictor would get if it
were allowed to know the held-out majority. It is reported to size the
holdout, not to be quoted as a result: the holdout is only informative
because peeking buys 0.51–0.83 where honest shortcuts buy nothing.

## 5. Task validity

**Saturated (majority ≥ 0.95).** S 0.985, T 0.998, U 0.975, V 0.995. A beat
here proves nothing. The repo's README already marks these SATURATED.

**Single-label — cannot discriminate at all.** B, F, G, I, J each have
exactly one label among scored rows. B is the largest at 228 rows and
scores 1.000 from a constant. This is worse than saturation: a saturated
family at least has a minority class to find, whereas these cannot be
scored by anything, including a model that reads every input perfectly and
answers wrongly.

**Held-out sides too small to estimate.** M has **1** test row, T has **2**,
N has **3**, E has **1**, L has 29. M and T pass every repository gate.

**Trivially unanswerable.** Family B's scored projection is
`invariant_stated`, which is `true` for all 228 scored rows by construction —
its `unlabelled_reason` for the other 492 says no source states a violated
invariant. The task reduces to "was an answer key produced?"

**Genuinely ambiguous.** 6 K rows name more than one candidate language in
their evidence, so "which language does this concern?" has no unique answer
from the payload alone.

**Non-scorable, reported not zero-filled.** D (720 rows, generative),
H (7, descriptive), Q (137, judge-graded) carry `skipped_no_scorable_key`
with a reason. They are never counted as zero.

### What the benchmark can reliably measure

Only family **A** (`vulnerability_detection`) is clean on every axis checked:
two classes, 720 scorable rows, 147 held-out, zero record/code/repo
overlap, no near-duplicates, no answer in evidence, label-mix distance 0.340.
It remains near-degenerate in absolute terms (0.73 majority) and its class
prior moves across splits, so a model must beat **0.551 on test**, not the
0.8725 micro figure.

**C** (`attacker_reasoning`) is the only family with a genuine multi-class
label space, clean leakage, zero repo overlap and the largest measured
near-duplicate separation — but its held-out label mix is 1.030 L1 from
train, so a score there is also a statement about the split.

## 6. Prioritized findings

| # | Severity | Finding | Evidence |
|---|---|---|---|
| 1 | **Critical** | K, O, P group key determines the label; a lookup table scores 1.000/1.000/0.903 at 100% coverage | `audit.json` `source_only_lookup` |
| 2 | **Critical** | R's held-out splits are 100% tier 2 from a contest prefix absent from train; train-majority scores 0.000 while retrieval scores 1.000 | `audit.json` `split_drift` |
| 3 | **High** | Input retrieval scores 0.839–1.000 on official splits and 0.000 on every class-disjoint holdout | `secondary_holdout_manifest.json` |
| 4 | **High** | 5 of 19 families are single-label; B scores 1.000 from a constant across 228 rows | `audit.json` `degeneracy` |
| 5 | **High** | `baseline_first_published.json` publishes `accuracy = 1.0000` at 0.32% coverage | `reports/baselines/` |
| 6 | **High** | S, T, U, V are ≥0.95 majority; 14,815 of 22,149 scorable rows (15,075 across all nine ≥95% families) | `audit.json` |
| 7 | **Medium** | K leaks the gold language into evidence in 78/137 rows; L leaks severity in 94 | `audit.json` `answer_leakage` |
| 8 | **Medium** | M/T/N/E have 1–3 held-out rows | `audit.json` `split_drift` |
| 9 | **Medium** | Macro-F1 is never published; it halves V (1.000 → 0.500) and quintuples the gap on U (0.198) | §3.2 |
| 10 | **Low** | T's 2 test rows are exact near-duplicates of train rows with the same label | `audit.json` `near_duplicates` |

### Recommended fixes, in order

1. **Fix the `source_id` leak in V/U inputs** or drop the field from the
   model-facing payload. It is a one-line change to the payload and it
   removes finding 1 outright.
2. **Re-split R** so validation and test are not single-contest,
   single-tier. Until then R cannot be scored.
3. **Regroup K by something other than the record id's language prefix**,
   or drop K — its ceiling is a lookup table either way.
4. **Retire B, F, G, I, J from the scored set** or relabel them. A family
   with one label should be reported as unscorable rather than scored 1.000.
5. **Publish macro-F1 and coverage alongside every accuracy**, and rename
   `micro.accuracy` to something coverage-qualified.
6. **Add held-out rows to M, T, N, E**, or mark them non-evaluable.

## 7. Remaining validity threats

Threats this audit does **not** resolve:

1. **No model was run.** Every number here is a shortcut or a structural
   measurement. Whether a real model can beat the 0.551 floor on A, or
   whether retrieval genuinely helps a human, is untested. This report says
   what the benchmark *permits*, not what any model achieves.
2. **The class-disjoint holdout covers 4 of 19 families.** 15 were skipped
   for stated reasons. B/F/G/I/J can never be class-disjoint (one label);
   C/L/M/N/O need more minority support. No amount of splitting fixes a
   family that lacks the negative examples.
3. **A class-disjoint holdout cannot measure class-prior reasoning.** By
   construction the retained side has no example of the held-out labels, so
   a model cannot learn them at all — even a model with the correct
   inductive bias scores 0. This measures whether shortcuts transfer, which
   is what it is for; it is not a task any model can solve.
4. **Near-duplicate detection used 5-gram Jaccard ≤0.455.** A paraphrase
   with different wording would score low. Semantic duplication, shared
   boilerplate across publishers, and duplicated *findings* under different
   record ids are not detected.
5. **Grouping choices were mine.** Grouping by record, language prefix, or
   publishing source are three defensible definitions. A fourth — by
   auditor, by CVE, or by contract — could change the overlap verdicts.
6. **Code-level overlap was checked for A and C only**, the two families
   carrying code. K–Q carry prose and components; shared boilerplate prose
   between splits was not fingerprinted.
7. **The near-duplicate measurement is a Jaccard proxy, not a semantic
   check.** It is computed inside the gated audit (`near_duplicates` in
   `audit.json`), but it compares 5-gram token sets. It detects
   copy-paste, not paraphrase.
8. **Taxonomy leakage in T is unmeasured.** T's label comes from the
   auditor's own Category field; whether that category is recoverable from
   the title alone was not tested beyond the near-duplicate check.
9. **No held-out ground truth was re-derived.** Answer-key correctness was
   checked for *consistency with the records*, not by re-reading each source
   finding. A systematically wrong key in a family whose gold is 100%
   consistent (T) would be invisible here.

## Reproduce

Every command, with its result from a clean run:

| command | result |
|---|---|
| `python scripts/independent_benchmark_audit.py` | PASS — 19 scorable + 3 not scorable |
| `python scripts/independent_benchmark_audit.py --check` | PASS — committed audit current |
| `python scripts/build_secondary_holdout.py` | PASS — 4 class-disjoint, 7 group-disjoint built |
| `python scripts/build_secondary_holdout.py --check` | PASS — committed holdout current |
| `python -m unittest tests.test_independent_benchmark -q` | PASS — 25 tests |
| `python scripts/run_gates.py` | PASS — 17/17, 0 failed, 0 skipped |

The two new gates are `benchmark-audit-current` and
`benchmark-holdout-current`, registered in `scripts/run_gates.py` under
`--only benchmark`. Both run `--check` only, so a gate can never silently
regenerate the artifact it is verifying.

No existing benchmark file was modified. `git status` after a full audit and
holdout build shows only the new `benchmark/independent/` directory; the
same property is asserted byte-for-byte by
`TestAdditiveAndReproducible.test_building_the_layer_does_not_touch_benchmark_files`
and `test_audit_does_not_touch_benchmark_files`.

Determinism: `test_audit_is_deterministic` and `test_holdout_is_deterministic`
assert two runs at seed 7 produce byte-identical output. Everything is seeded;
no network is used; nothing is sampled from an unseeded source.

Outputs:

- `reports/independent/audit.json` — per-family leakage, degeneracy, drift,
  overlap, near-duplicate and baseline measurements
- `benchmark/independent/secondary_holdout_manifest.json` — split definitions,
  per-family verdicts and reasons for every skip
- `benchmark/independent/secondary_holdout_tasks.jsonl` — the holdout tasks,
  with `gold`, `group` and `original_split` for independent re-scoring
- `reports/independent_benchmark_evaluation.md` — this report
