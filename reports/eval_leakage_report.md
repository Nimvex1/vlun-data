## Method

- **protected evaluation set** — every row of every benchmark family whose split is test or validation. A record is protected if ANY family holds it out, because the split systems differ per layer (v1 splits_v2, v2.2 splits_v2_2, v3 splits_v3, vbeta by-source) and one record can be train in one and held out in another.
- **model visible corpus** — every .jsonl under training/. A corpus consumer globs a directory, so anything inside training/ is reachable; evaluation-side shards therefore live outside it.
- **id overlap** — benchmark identifiers (task id, record id, finding id, the source block, and the input's own finding id) against training identifiers (canonical_record_id, canonical_id, provenance.record_ref, example_id, id, task_id). A '::'-suffixed family prefix is stripped so 'A::test::x' and 'x' compare equal.
- **text overlap** — the model-facing payload, normalised to lowercase alphanumeric tokens, compared as ordered 8-word shingles. A row overlaps when min(|A|,|B|) containment of the shingle sets is >= 0.9, or when the normalised text is identical. Text shorter than 8 tokens is not compared.
- **code overlap** — exact code snippet bytes, snippets normalised for comments, literals and numbers, source file paths, and commit shas. An identical (or reformatting-invariant) snippet means the held-out task's evidence is in the training corpus and is counted as leakage. A shared file path or commit sha only means the same repository or revision was mined, which is provenance, and is reported separately.
- **label overlap** — for a benchmark row whose id also appears in the corpus, the answer-key fields are compared with the training row's supervised targets. The value mapping between the two vocabularies is derived from the family's TRAIN partition, never hand-written.
- **expected train overlap** — rows in a family's train partition share records with the training corpus by construction. That is the training data, not leakage; only the held-out partitions are defects.

Thresholds: `shingle_words=8`, `text_containment=0.9`, `min_text_tokens=8`, `max_shingle_posting=2000`, `max_candidates=400`

## Release boundary: what is open-key and what is protected

| evaluation | status | where the key is |
|---|---|---|
| benchmark families | **OPEN-KEY** | `in the family file itself` |
| canonical held out shards | **OPEN-KEY** | `benchmark/independent/canonical_holdout/` |
| secondary holdout | **OPEN-KEY** | `benchmark/independent/secondary_holdout_keys.jsonl` |
| v1 task holdout rows | **OPEN-KEY** | `benchmark/independent/v1_task_holdout/` |
| vlun prove private split | PROTECTED | outside the repository |

- **benchmark families** — every benchmark family row carries its answer key in the same file as its input; the key is committed, so every family is OPEN-KEY and no family may be described as hidden or protected against repository-level leakage
- **canonical held out shards** — the held-out partitions of the training views are committed, and are not model-visible because they live outside training/
- **secondary holdout** — the answer key is a separate file, committed in this repository and labelled OPEN-KEY; the model-facing task file carries the input and a task id only
- **v1 task holdout rows** — the task rows whose records a benchmark family holds out are committed, and are not model-visible because they live outside training/
- **vlun prove private split** — the key lives OUTSIDE the tracked tree and is committed to by SHA-256, so this evaluation IS protected against repository-level retrieval. scripts/build_prove_split.py refuses to write it inside the repository
