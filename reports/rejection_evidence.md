# Rejection evidence: what each count means

Generated by `scripts/build_rejection_corpus.py` (`rejection-definitions-1.0`). Every number is read from `derived_rejections/rejection_corpus.jsonl`; nothing here is typed in.

458 negatives, 458 with a publicly reported status, 9 with a reason attributed to a named judge or sponsor, 1 where the cited code removes the standing the claim asserts, 6 in total with a technical reason why the claim is false, 193 corroborated as a duplicate of an accepted finding, 0 where an exploit was attempted and the claimed violation was not demonstrated, and 256 where the public evidence stays insufficient. ## Definitions

**`rejection_status_publicly_reported`** — the contest page publicly records a status for this submission (duplicate / rejected / disputed / invalid / withdrawn / nullified / ineligible)

- evidence type: `observed_fact`; counts as a technical explanation: `False`

- this is the weakest useful statement: it is a fact about the contest record, not a reason the claim is false

**`reason_attributed_to_judge_or_sponsor`** — a named judge or the sponsor published a statement, carried verbatim with author, role, URL and excerpt hash, that addresses this submission

- evidence type: `externally_attributed`; counts as a technical explanation: `conditional`

- split by rule into a technical refutation and a design-intent/scope exclusion; participant (warden) replies are excluded — they are discussion, not an adjudicated reason

**`reason_supported_by_cited_code`** — a guard mechanically located on the function the submission says the attacker calls removes the standing the submission's own text claims

- evidence type: `derived_fact`; counts as a technical explanation: `True`

- requires the gate on the CLAIM'S OWN TARGET plus a claim that asserts an actor lacking that role; a gate elsewhere, or a claim about a privileged actor, is recorded as context only

**`claim_corroborated_as_duplicate_of_confirmed_finding`** — the same claim was accepted as a confirmed/acknowledged finding in the same audit, so the underlying issue is real and only this copy was redundant

- evidence type: `derived_fact`; counts as a technical explanation: `False`

- graded by method: an explicit `duplicate_of` pointer that resolves to a published finding is high confidence, an identical normalised title in the same audit is medium, a shared code target or similar snippet is context only. Corroboration supports `is_false_positive: false` for the underlying issue; it never supports a technical reason

**`exploit_attempted_and_claimed_violation_not_demonstrated`** — an exploit was reconstructed and executed against the pinned revision and the claimed violation was not observed

- evidence type: `experimentally_verified`; counts as a technical explanation: `True`

- the only class that can establish a false positive by experiment. Where the attack was executed and succeeded, the record states the underlying issue is real rather than calling anything disproven

**`unknown_or_insufficient_evidence`** — only a rejection, duplicate or dispute label is public, no attributed reason exists, no gate refutes the claim's own standing, and no exploit was attempted

- evidence type: `unknown`; counts as a technical explanation: `False`

- unknown_or_insufficient_evidence is a valid answer, not a failure of the pipeline; it is reported with the blocker that applies (pointer unresolved, environment unavailable, no public statement)


## Reason classes

A record carries every class that applies, plus one primary class chosen by the precedence order below.

- primary precedence: `executionally_disproven` > `public_judge_or_sponsor_explanation` > `business_scenario_exclusion` > `code_derived_blocker` > `experimentally_confirmed_underlying_issue` > `corroborated_duplicate` > `withdrawn_by_author` > `scope_or_eligibility_label` > `dispute_or_invalid_label` > `duplicate_label_unresolved_pointer` > `unattributed_participant_discussion` > `code_gate_context_only` > `unresolved`

## The two distinctions this layer exists to enforce

1. **Corroboration is not explanation.** A duplicate pointer at a confirmed finding says the underlying issue is real and this copy was redundant. It is not a statement about why the claim is technically false, so it is excluded from the technical-reason count even though it does support `is_false_positive: false` for the underlying issue.

2. **A guard on a function is not a refutation.** `onlyOwner` on a function refutes "anyone can call this", not "the owner can do harm with this". The gate axis above shows how many code-derived blockers were demoted to context because the claim's own text does not depend on the standing the gate removes.


## Unknown is a valid answer

`256` records stay `unknown_or_insufficient_evidence`. A report is not invalid because a judge's rationale is unavailable; the blocker is recorded per record (unresolved `duplicate_of` pointer, environment unavailable, or no public statement) rather than being filled with an invented reason.


## Where these records come from

Every row in this layer comes from a public Code4rena contest record in `jsonl/negative_findings.jsonl`. No artefact of a report the dataset builder submitted to a bounty programme exists in this project, and none was invented to reach 458-plus records: seeding one would require the actual source artefact plus a check of the programme's publication and confidentiality terms, and personal details would have to be anonymised first.
